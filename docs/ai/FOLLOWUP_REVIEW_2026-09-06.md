## V2-01：把媒体归类的提交点与补偿边界分清楚

**入口**：`src/GameSaveCenter.Worker/Services/MediaSyncService.cs` 的 `ApplyClassificationPreviewAsync`、`UndoClassificationBatchAsync`、`RestoreMovedClassificationCopyAsync`；`Persistence/SqliteStateStore.MediaClassification.cs`。

**触发路径**：先移动归档副本，再执行 `TryApplyMediaClassificationAsync` 更新 media 行，随后写批次条目和审计。这些不是一个事务。如果 media 更新已经成功，后续批次或审计写入抛异常，catch 会把文件搬回，但没有逆向更新已提交的 media 行；数据库仍指向新路径。撤销流程也有相同的提交后补偿问题。取消分支把已取消的 token 用于回滚，回滚本身可能立即取消。文案“原副本保持不变”也不能覆盖回滚失败情况。

**方案**：

1. 将 media 条件更新与批次条目的 Applied/Undone 状态放入同一个 SQLite 事务，先定义明确的 durable commit 点。
2. 审计独立于已提交业务：提交后审计失败只报告审计失败，不能只回滚文件；提交前失败才执行补偿。
3. 文件与 SQLite 无法共用原子事务，移动前持久化意图及两端路径/哈希，启动时协调未完成条目；可借鉴保留清理账本，但不要机械套用删除语义。
4. 使用独立有界恢复 token；补偿失败保存 RecoveryRequired 与真实路径，禁止无条件提示恢复成功。并发应用/撤销同一媒体需要条目级互斥或可恢复占有状态。

**验收**：移动后、media 更新后、批次更新时、审计写入时分别注入失败；同样覆盖撤销、取消及独立进程中断。每次重启后数据库路径指向有效副本或有明确恢复项；原始媒体不移动/删除，不覆盖用户后续编辑。现有正常应用/撤销与预览后冲突测试继续通过。

## V2-02：健康巡检的后台循环与计划同步

**入口**：`HealthInspectionService.ExecuteAsync`、`RunNowAsync`、`SyncPlanAsync`。

**触发路径**：手动 RunOne 写入 `LastStatus=Running` 与 `LastStartedUtc` 后，后台 `IsDue` 认为 in-flight 状态到期；`_runGate.WaitAsync(0)` 因手动巡检持锁而返回 false，该分支没有 Delay/等待，循环立即重新查询 SQLite。由此可能持续争抢 CPU/数据库，实际负载尚未测量。此外循环最外层的初始计划同步和状态读取不在异常隔离中；存储临时异常可使后台服务任务异常退出。不能仅凭内部 RunOne 的 catch 声称整个服务有隔离。

**方案**：后台等待信号或使用可取消的有界延迟，获锁后重新读取状态；区分“本进程正在执行”与“上个进程遗留的 in-flight”。外围捕获可恢复存储异常并退避，应用停止正常退出。SyncPlan 与完成状态目前都整行读改写，应通过版本/CAS 或分别更新配置字段与执行字段，避免设置变更被旧 state 写回。

**验收**：用可控闸门阻塞手动验证 5 秒，断言后台读取次数有上限而非只断言最终状态；运行中修改启用/间隔，完成后配置仍有效；瞬时读取失败后恢复；退出时无无界重试。不要用长时间真实解包充当计时夹具。

## V2-03：巡检恢复游标、推迟公平性与过期语义

**入口**：`HealthInspectionService.RunOneAsync`、`SelectCandidate`、`CompleteAsync`；`HealthInspectionServiceTests.StatePersistsInFlightCursorAcrossRestart`。

**源码事实**：

- Running 状态在选候选之前保存；选定后只修改内存里的 Cursor，验证前没有再落盘。硬中断时不保证保存的是正在验证的备份身份。
- SelectCandidate 总是先选未验证/过期集合的第一个；若它所属游戏一直运行，Deferred 后仍会被优先选中，其他游戏可以长期得不到检查。
- 全部验证仍新鲜时，代码仍回退到轮转候选，并非“不需要检查”；轮转排序包含 CreatedUtc，但游标比较只包含 GameId/BackupId，排序与游标并不一致。
- 现有 `StatePersistsInFlightCursorAcrossRestart` 人工创建带游标状态并重开存储，证明的是存储读写，未证明服务自己在解包前写入该候选。

**方案**：选候选、记录身份和 Running 一起持久化成功后才开始验证；恢复明确优先处理持久化 in-flight。为 Deferred 候选记独立下次可试时间，本轮可寻找其他可用游戏；采用与排序完全一致的复合游标。计划巡检无过期项时返回 UpToDate；手动强制重验作为显式选项。一次临时 I/O/预算失败与“确证归档损坏”分开描述，失败后提供重新验证入口，避免用户误解恢复拦截的原因。

**验收**：A 游戏长时间运行而 B 正常可检查；全新鲜集合不重复解包；实际服务进入验证前读 SQLite 核对候选；硬中断后即使新增优先级更高备份，仍按既定恢复策略处理 in-flight；同时间不同 ID、公平轮转、旧候选已删除、状态写失败均有行为回归。

## V2-04：RequestId 必须绑定请求内容

**入口**：`Persistence/IpcRequestLedger.cs` 的 `ClaimIpcRequestAsync`；`Ipc/NamedPipeServerService.cs` 的 `DispatchWithReplayProtectionAsync`。

**触发路径**：账本保存 type，但认领后只读 state/response，未核对 type，也不保存 payload 指纹。同一 ID 携带不同游戏/动作/参数，会返回此前操作的响应或处理中状态。这不是当前正常随机 ID 流程必然出错，而是未来客户端重试/集成容易踩到的协议边界。空 RequestId 的受保护请求还会直接绕过账本。

**方案**：持久化消息类型、契约版本和规范化负载指纹；相同 ID 内容不同返回稳定 `REQUEST_ID_CONFLICT`，不执行也不重放旧响应。明确旧账本迁移、缺少 ID 的兼容策略及保留期；不简单把客户端合法重试判成新请求。将当前只在启动执行的 7 天清理扩展为低频有界维护，保留未协调请求的必要证据。

**验收**：相同 ID 相同内容重放；不同 type、游戏、恢复版本、确认字段冲突；JSON 属性顺序变化按规范化策略处理；重启、账本过期、旧记录无指纹；错误响应仍与请求身份一致。

## V2-05：云端 check 的取消不是上传任务

**入口**：`CloudTransferStateService.VerifyAsync`、`CloudTransferCoordinator.RunUploadAsync`。

**触发路径**：Verify 先将持久化状态设为 Transferring，然后等待全局 gate 并执行 check；后面的状态分支只处理返回结果。等待 gate 被取消或调用抛异常时，不会走状态收尾。协调器可以释放运行中记录，但持久化队列仍显示传输中；启动恢复也无法从该行区分之前是上传还是纯校验。

**方案**：保存 OperationKind=Upload/Verify 或为只读校验单独持久化状态；排队与实际传输分别显示。try/catch/finally 收尾取消和异常，保留此前 Uploaded/RemoteVerified 保证及验证时间，不能让未完成 check 提升保证等级。增加操作代际/CAS，迟到的校验不得覆盖新上传。恢复旧记录时不得因取消纯 check 而擅自转成上传请求。

**验收**：等待 gate 时取消、工具启动失败、执行中取消、返回失败、成功后落盘失败、Worker 重启；队列最终可解释且无永久 Transferring，纯校验取消不产生意外上传，不删除本地/远端内容。

## V2-06：云队列摘要不要再次混淆加载窗口与全集

**入口**：`CloudTransferStateService.GetStatusAsync`；`SqliteStateStore.CloudTransfers.cs`。

**证据**：队列表和旧重试表各只读最近 1000 行，随后与游戏/媒体基础状态合并并统计；基础状态可补部分条目数量，但不能恢复被截掉条目的次数、错误码、下次时间等。最终 UI 明细又取前 100；摘要中的 NextAttemptUtc 也依赖上述内存集合。不能简单宣称总数一定等于 1000，但不能保证全量状态统计和最早重试时间准确。

**方案**：SQL 先按真实完整数据计算摘要和最早重试时间；明细独立分页，兼容旧队列按稳定键去重。按当前过滤结果显示“已加载/共计”，可按失败/认证/校验/类型查询。与任务摘要分离但复用其契约经验。

**验收**：超过 1000 个键、最新 1000 外有最早重试/认证失败、同游戏备份和媒体两个类型、旧新表同键；摘要不受页码影响，未加载失败项仍可找到。

## V2-07：长列表累积成本与查询快照

**入口**：`DashboardViewModel.Media.cs` 的 `ApplyMediaPage`、`MergeMediaItems` 和 Inbox 同类路径；`SqliteStateStore.MediaQueries.cs`。

**证据**：首批已经按需加载 200 条，旧 5000 截断已解决。但加载更多会遍历已加载集合生成合并列表并整体 Replace；客户端没有页缓存上限。连续加载所有页面的累计合并工作随页数增长，列表虚拟化只限制视觉容器，不限制 DTO/合并分配。数据库每页独立执行 COUNT 和 SELECT，两者没有同一读事务；计数漂移属于可定义的并发一致性边界，而非目前已经复现的漏项。

**方案**：先测多页连续加载与后段搜索，确定热点再使用按 ID 索引的增量追加/更新；可按页设置有界缓存，选中项和草稿单独保留。明确是实时列表还是快照列表，前者提示“有新内容可刷新”，后者使用查询身份/上界；总数缓存失效或按读事务获得页级一致视图。不要为了缓存而破坏当前 Item 滚动和 Recycling。

**验收**：连续加载 250 页的时间、分配量、集合通知数量与 GC 后保留量；快速筛选/卸载、归类期间翻页、当前选中草稿保留；不仅测试 Worker 单页 SQL，也不把这里的复杂度推导写成实测 UI 卡顿。
