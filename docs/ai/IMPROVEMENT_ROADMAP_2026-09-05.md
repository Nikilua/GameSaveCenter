## R01：任务终态写入失败不能锁死同一游戏

**证据**：`src/GameSaveCenter.Worker/Services/TaskCoordinator.cs` 的 `RunAsync` 在 `finally` 中先 `await PersistAndPublishAsync(..., CancellationToken.None)`，之后才 `_taskTokens.TryRemove`、`gate.Release`。SQLite 写入异常会跳过后二者；同游戏后续任务可能一直等待，取消令牌表也保留已释放对象。正常路径测试通过不能覆盖这条路径。

**实施**：

1. 把终态持久化放入内层 try，令牌移除和锁释放放入不依赖持久化成功的内层 finally；仅在成功进入锁后释放。
2. 区分“业务执行成功”和“终态记录写入失败”，记录 TaskId、GameId、原始业务结果和持久化异常。不要向 UI 发布未成功落盘的成功事件，也不要无上限重试。
3. 若需注入失败，抽取最小任务存储接口或局部测试接缝，不重构整个 SQLite 层。

**验收**：业务成功、失败、取消三条路径分别注入最后一次写入失败；断言下一同游戏任务在有界时间内获得锁、令牌表清理、不同游戏不受影响，且原始错误可追踪。正常终态事件顺序保持不变。

## R02：全局清理必须绑定具体候选并参与互斥

**证据**：`RetentionSimulationService.ApplyAsync` 仅比较预览时间、候选总数和总字节；A 被替换为同大小 B 时仍可通过。循环里的 `current` 来自此前载入的 `group.Versions`，不是逐项重读数据库。该服务没有使用 `GameOperationLock`，`IpcRequestDispatcher` 直接调用它，而备份/恢复使用该锁。因此预览之后或执行期间保护状态变化存在竞争窗口。

**实施**：

1. 预览返回服务端生成的 PreviewId，并持久化/保存完整候选清单和版本指纹：GameId、BackupId、规范化路径、大小、保护状态、策略版本等；UI 的前 200 条仍只是展示，不充当执行清单。
2. 执行消费同一预览，明确过期与重复提交行为；不能只增加客户端可任意替换的 count/hash。
3. 每游戏获取现有操作锁，重读版本/策略并核对指纹。备份、恢复、保留清理及修改锁定状态的入口必须形成同一互斥约定；单给清理加锁不能保护未参与锁的元数据更新。
4. 定义锁顺序避免 TaskCoordinator 与 GameOperationLock 反向获取。推荐逐游戏短批处理，不同时持有整库所有游戏锁；有变化的游戏跳过并要求重新预览，明确部分完成结果。
5. 规范路径前缀检查之外，复用已有路径安全设施检查 reparse point/junction 边界；不存在的文件跳过，不猜测替代路径。

**验收**：候选 ID 改变但数量/体积不变、确认后锁定、同时恢复、同时新建备份、预览重复提交、路径重定向、取消；未获确认的替代候选不得删除，受保护项不得删除。使用临时夹具目录完成，不触碰真实存档。

## R03：隔离区做成可恢复状态机

**证据**：`RetentionSimulationService` 将 ZIP 移到随机批次的 `.pending` 文件后删除索引。数据库失败时 `TryRestoreFromQuarantine` 吞掉恢复异常；当前失败摘要没有包含实际 quarantinePath，也没有持久化“原路径→隔离路径”的账本。源码搜索未发现该隔离区的专用启动恢复器。`FreedBytes` 在隔离文件最终删除失败时仍累加，容易把逻辑移出量解释成真实释放空间。

**实施**：新增清理批次/条目账本（Planned、Moved、IndexRemoved、Deleted、RecoveryRequired）；移动前记原路径/目标路径/文件身份，步骤完成后推进状态。Worker 启动只扫描并协调未完批次，维护页显示可恢复项；不因启动而删除无法确认归属的文件。区分已移出归档字节、真正释放字节、隔离占用字节，恢复失败保留完整定位信息。

**验收**：在“记账后、移动后、删索引后、删文件前”分别中断独立 Worker，重启后可确定恢复/待处理状态；多次协调幂等；原路径已有新文件时绝不覆盖；删除失败时实际释放空间不虚报。依赖 R02 的候选身份契约。

## R04：任务统计与历史查询说清楚范围

**证据**：`DashboardService.GetAsync` 只取最近 50 个任务；`IpcRequestDispatcher` 的 `GetTasks` 固定最多 200。`DashboardViewModel.CompletedTaskCount` 统计 `Tasks` 中所有 Succeeded，没有日期判断，但 `TaskCenterView.xaml` 标注“今日完成”；“任务总数”也绑定 `Tasks.Count`。这会把历史成功计入今日，并把加载窗口当成全集。Dashboard 云端等待数同样依赖最近任务窗口。

**实施**：

1. 第一小提交修正明确文案/日期口径：暂时只能计算加载集时显示“已加载任务/最近任务成功”，不要声称全局今日总数。
2. 新增 TaskQuery 和 TaskSummary 契约；服务端过滤状态、游戏、类型、时间范围，返回稳定分页与总数。今日使用用户本地日期换算 UTC 半开区间，明确跨午夜刷新和夏令时。
3. 摘要独立 SQL 聚合；所有活动任务单独查询，不能因新任务多而从“运行中”消失。
4. 任务列表增加“最近/历史”和日期范围；批量重试明示“当前结果/当前选中”，展示实际去重后的计划与跳过原因，复用现有安全重试分流。

**验收**：昨天成功、今日成功、跨午夜长任务、50/200 条之外仍运行、10000 条历史、相同创建时间；摘要与分页无关，搜索能找到窗口之外的失败任务。保持现有 SQLite 索引，新增索引必须用查询计划证明必要性。

## R05：下拉框提交不能只覆盖鼠标展开选择

**证据**：生产 Shell 与兼容 Dashboard 的游戏筛选都使用 OneWay 显示和 `DropDownClosed` 提交，解决了程序化选择抢写。该入口是否覆盖关闭下拉时的方向键、字符搜索以及 UI Automation 选择，需要真实 WPF 行为测试；不能直接宣称当前键盘已坏。

**实施**：先编写 STA 行为测试复现完整控件交互。若出现控件显示变了而 VM 不变，抽取共享筛选提交 behavior，显式区分绑定同步与用户操作，覆盖键盘/Automation；两套选择器复用一个实现。不要简单恢复无守卫 TwoWay 或在所有 SelectionChanged 无条件写回。

**验收**：鼠标、关闭下拉时方向键、Alt+Down、Enter/Esc、字符搜索、Automation Selection、Loaded、ItemsSource 重建、双实例同时存在、保存重启。各入口的显示值/VM 值/过滤结果一致，取消不误提交，程序化同步不抢写。

## R06：媒体从“传输分页”升级为“界面按需分页”

**证据**：`DashboardViewModel.Media.cs` 按 500 条循环，最多 5000 条，全部收齐后才返回 UI；超过上限没有继续加载路径。`SqliteStateStore.Media.cs` 使用 `ORDER BY captured_utc DESC, media_id DESC LIMIT/OFFSET`，加载期间新增/归类会改变后续 offset。已有旧代际取消和列表虚拟化应保留。

**实施**：

1. DTO 增加 Items、TotalCount、HasMore、NextCursor；首批建议 100～200 条，第一批完成就显示，其后按“加载更多”或近底部预取。
2. 使用 `(captured_utc, media_id)` 稳定游标；定义扫描中插入新数据的快照/刷新语义，不把首批新项目塞入正在浏览的旧分页序列。
3. 筛选/搜索下推服务端，代际变化取消旧页；内存页面缓存设上限，选中项按 ID 保存。
4. 明示已加载/总数；批量操作区分选中项与全部搜索结果，服务端处理后者并返回逐项结果，不将“全选”默认为仅内存中的条目。
5. 保留当前生产 Item 滚动及 Recycling 虚拟化，不借此恢复历史有问题的 Pixel 滚动方案。

**验收**：0、499、500、5001、50000 项；后段条目能搜索访问；加载期间新增/归类不重复漏项；快速换模式旧页不回写；首批所需 IPC 次数恒定，缓存有界；任何消息不超过 4 MiB。性能数值先测基线再定门槛，不能承诺未测的毫秒收益。

**实施记录（2026-09-05）**：新增 `MediaQueryDto`/`MediaPageDto` 与三类媒体分页 IPC，Worker 采用 `(captured_utc, media_id)` 稳定游标，服务端支持类型、收藏、关键词过滤并返回独立总数；保留旧列表消息兼容已有客户端。新增游戏/分类复合索引，并用 `EXPLAIN QUERY PLAN` 验证当前游戏与收件箱查询命中索引。Dashboard 首批请求 200 条，当前游戏与待归类/已忽略列表均支持“加载更多”、按模式独立保存游标和总数，搜索与过滤变化会取消旧代际并重取首屏；现有选择、批量操作、Item 滚动与 Recycling 虚拟化保持不变。Release 构建 0 warning/0 error；Core `65/65`、Worker `255/255`、Playnite `333/390`（57 跳过）、XAML `19/19` 通过，源码校验和 `git diff --check` 通过。尚未在真实 Playnite 宿主完成 50,000 项、4 MiB 边界和长时 UI 性能实测。

## R07：IPC 取消与业务取消分开建模

**证据**：`WorkerIpcClient.RequestAsync` 只有 timeout，没有调用者 CancellationToken；连接/写行也未贯穿该 token。现有页面代际保护可丢弃结果，但不能及时结束当前请求等待。

**实施**：增加可选调用者令牌，联结超时和页面/插件生命周期；覆盖连接、写入、读取、Dispose 的竞争。分别报告用户取消、宿主退出、超时、管道断开。只读请求可安全停止等待；备份/恢复等写请求一旦提交，不把断开连接解释为事务撤销，返回/追踪 RequestId 与 TaskId，超时后查结果再决定重试。需要远端取消时走现有任务取消语义；新增幂等键时规定持久化期限、重复请求响应和重启恢复。

**验收**：连接前/写入中/读取中取消、退出时请求挂起、服务器完成但响应丢失、超时后重试；不会重复备份或恢复，不遗留读取任务，不把用户取消显示成失败。兼容 net462，不直接照搬仅现代 .NET 可用的 Stream API 重载。

**实施记录（2026-09-05）**：Playnite IPC 客户端增加调用者令牌与宿主退出令牌，连接、写入、读取均通过有界竞态等待；取消会先结束调用者等待，再异步关闭管道，避免 `StreamReader`/原生读写 Dispose 竞态。用户取消、宿主退出、超时、管道断开、连接失败和 Worker 的“请求处理中/已中断”分别建模；页面详情、当前媒体分页和媒体收件箱分页均接入请求级取消，代际检查继续作为响应回写边界。

写请求使用客户端生成的 RequestId；Worker SQLite 持久化 7 天请求账本，重复请求只重放已完成响应，同请求处理中不重复执行，Worker 重启会把未完成请求标为不可自动重放的 Interrupted。Backup/Restore 返回的 TaskStatusDto 与 RequestId 关联，任务查询支持按 RequestId 精确核对；超时或断管后的恢复请求使用同一 ID，并在短窗口内等待原请求完成。旧构造器和 net462 可用 API 保持兼容，远端取消仍走现有 CancelTask 语义。

新增账本、任务关联、客户端取消/重放源码回归；真实 Named Pipe 行为套件覆盖连接前、读取中、宿主退出、响应丢失重放和写入中取消共 5 项。Release 构建 0 warning/0 error；Core `65/65`、Worker `258/258`、Playnite `333/395`（62 跳过）、XAML `19/19`、源码校验通过。当前受限执行环境拒绝创建本地 Named Pipe 客户端，因此 5 项真实管道测试由能力探测跳过；完整 Windows/Playnite 环境会执行，真实宿主、Worker 重启和长任务仍待人工复核。

## U02：动画先测成本，再统一状态反馈（侧栏试点已完成）
