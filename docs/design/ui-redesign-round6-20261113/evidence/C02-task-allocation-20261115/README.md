## 方法

- SDK 8.0.423、Release、同一 Windows 11 主机；固定样本时刻 `2026-11-13T00:00:00Z`，深色主题、960×640 DIP、8 条合成任务、选中 T-0001。候选和基线都采用相同 `FakeDashboardData.CreateTaskComparisonFixture()` 与相同 Harness 文件哈希。
- 每个独立进程先生成并布局一个真实 WPF `Window`。首次页面分配从创建 `Application` 前计数，到第一轮 `Window.Show()`/`UpdateLayout()` 后计数；不含进程启动，包含首次应用、夹具、View 与布局初始化。
- 稳态分配用运行时 `GC.GetAllocatedBytesForCurrentThread()` 计数器，通过一次性反射解析后的 `Func<long>` 委托调用。每个按钮操作的字节差直接包住路由 `Button.Click` 和同步 `Window.UpdateLayout()`；新建的 `RoutedEventArgs` 计入样本。不是 `GC.GetTotalMemory`、保留堆或 Rendering 间隔代理。
- 每进程预热 10 组开合；随后测 24 组、24 次打开和24次收起，顺序交替 `close-open` 与 `open-close`。23 次状态预置点击不计入分配样本，明细写在各 TSV。每组开始/终止状态、选择稳定性均有断言。未手动调用 GC；报告记录期间 CLR 自发回收次数。
- 四次独立进程按基线、候选、候选、基线（B-C-C-B）运行。各次均在 `WinSta0` 私有桌面，输入桌面前后为 `Default`，构建和探针直接 exit 0，0 warning/0 error。WPF 报告显示 1.00 logical DIP；它不代表显示器物理 DPI。所有逐项原始报告、TSV 和桌面身份在 `runs/`。

预热期间两侧每次均记录 Gen0/Gen1/Gen2 = 16/1/0；测量期间基线为40/2/1，候选为39/2/1。采样期间发生 CLR 自发回收，没有强制 GC。候选每组开合分配低约1.88%，未观察到回退；该结果只说明受控任务详情按钮与布局操作的托管分配量。

## 边界与诊断

输入来自受控 WPF 窗口上的程序化路由按钮事件，不是鼠标、键盘、Playnite 宿主或 UIA 客户端。没有读取/写入真实用户配置、Playnite profile、游戏存档或云端。此测量不验证真实画面帧、DWM、物理 DPI、真实输入延迟或动画流畅度。

初次构建暴露 net472 编译引用未声明运行时分配计数 API；已改为一次性反射发现后缓存委托，并用 1 KiB 校准分配验证计数器。早期受控探针也发现紧凑详情收起按钮只在展开后加入视觉树，以及正反序列需要规范化终态；两处均修正。原始失败诊断保留在 [diagnostics](diagnostics/)；没有跳过测试或扩大 skip。
